## 4. AUTH-P0 — serwerowy broker i HttpOnly BFF

### Wariant badany, nadal PROPOSED

Trasy AUTH i testowe formularze/provisioner żyją w osobnym project-dir Next `experiments/foundation/auth/web/`, nie w root `src/app`; build eksperymentu nie jest obrazem release. Dopiero PR-F6 integruje zatwierdzone adaptery z root aplikacją i powtarza testy na buildzie produkcyjnym, bez kopiowania testowych hooków.

Rekomendowany **wariant eksperymentalny**, zgodny z zatwierdzonym kierunkiem BFF: przeglądarka posiada wyłącznie losowy opaque session handle w cookie `__Host-jobs_session`; access/refresh tokens oraz PKCE verifier są obsługiwane wyłącznie na serwerze. BFF zwraca minimalne DTO, nigdy obiektu Supabase session. Rich UI nie używa browser Supabase Auth/Data API client. Nie jest to zmiana dostawcy Auth ani zatwierdzony nowy produktowy session contract.

PoC brokera używa wydzielonego, nieeksponowanego technicznego storage z losowym handle zapisanym jako hash, powiązaniem owner/session_id, zaszyfrowaną parą tokenów i numerem generacji. Szyfrowanie uwierzytelnione i klucz poza DB; klucz nie trafia do NEXT_PUBLIC ani snapshotów. Proponowane minimalne uprawnienia: oddzielna wewnętrzna rola DB z dostępem tylko do tego storage, bez dostępu do danych użytkowych/Auth internals. Nie jest to service-role do zapytań użytkownika; user CRUD nadal korzysta z Data API i JWT właściciela. Przed implementacją powstaje jawny manifest schematu/grantów, threat model oraz model kluczy i rotacji, ocenione przez security review. Ten storage, model kluczy oraz uprawnienia wymagają osobnej autoryzacji PoC i security review **przed** ich implementacją. Nie są domyślnym produkcyjnym schematem.

Powód wyboru do badania: trwały storage umożliwia synchronizację refresh pomiędzy dwoma procesami, unieważnienie pojedynczego handle i listę własnych urządzeń bez przenoszenia tokenów do JS. Stateless zaszyfrowane tokeny w cookie można porównać jako węższy eksperyment, lecz nie deklarować, że rozwiązują selected-device logout i refresh concurrency. Nie wybierać alternatywnego modelu sesji bez PO. Manifest brokera minimalizuje metadane urządzenia: PoC ma wyłącznie syntetyczne etykiety kontekstów; nie dodaje automatycznie IP/user-agent ani śledzenia urządzeń. Jakiekolwiek produktowe metadane, retencja i usuwanie wymagają OPEN-032/042.

Cookie produkcyjnego kontraktu badawczego: `HttpOnly; Secure; SameSite=Lax; Path=/`, bez `Domain`, z rotacją handle po logowaniu i unieważnieniu. Handle generowany CSPRNG z co najmniej 256 bitami entropii; w DB tylko jego hash. To propozycja mechanizmu PoC, nie czasów sesji produktu. Lax umożliwia top-level GET callback; nie zastępuje CSRF. Pełny test Secure wymaga lokalnego HTTPS z zaufanym certyfikatem; test na HTTP/localhost sam go nie dowodzi. Czasy cookies/tokenów/recovery są jawnie krótkimi parametrami fixture do wymuszenia wygaśnięcia, **nie** rozstrzygnięciem OPEN-042/043 ani wartością MVP.

### Bramka AUTH

PoC jest zakończony technicznie tylko po wykonaniu AUTH-01–13 na dokładnie wskazanym kandydacie, łącznie z HTTPS, dwoma procesami, kontrolowaną awarią refresh i rzeczywistym Google flow. Niewykonany scenariusz pozostaje `NOT RUN`; nie zastępuje go opinia reviewera. Wznowienie po FAIL wymaga poprawki + ponowienia dotkniętych testów + niezależnego review. Zaliczenie mechanizmów nie zamyka polityk `OPEN-013/042/043/046` ani nie autoryzuje publicznych kont. Jeżeli zachowany, odwołany JWT nadal uzyskuje dostęp do Data API, wynik nie może być opisany jako skuteczna natychmiastowa revocation: raport podaje lukę i czas, a dopuszczenie pozostaje `BLOCKED` do rozstrzygnięcia wymaganej semantyki/okna przez PO. Samo ograniczenie ważności JWT nie jest automatycznie zaakceptowanym obejściem. Cofnięcie handle w brokerze dowodzi tylko granicy BFF.

**Wariant po negatywnym wyniku:** zachować zamrożony dowód i przyczynę; kontynuować niezależny RLS/RPC na fixture JWT, wstrzymać zależny biznesowy Auth/public signup. Przedstawić PO/Tech Lead minimalną korektę implementacji brokera w tym samym HttpOnly+BFF modelu. Jeśli wymagane są nowe uprzywilejowane funkcje Auth/session-active RLS, inny storage lub inne granice zaufania, przygotować analizę bezpieczeństwa i dopiero po decyzji ADR. Nie obniżać HttpOnly do cookies czytelnych w JS ani nie zmieniać dostawcy samodzielnie.

## 5. DB/RLS-P0 — środowisko, migracje i izolacja

**Wykonanie F2 autoryzowane 2026-10-29:** syntetyczny kontrakt i bezpośrednia kolumna Data API macierzy są implementowane w osobnym PoC. [Raport F2](foundation-f2.md) zawiera aktualne wyniki i ograniczenia; poniższe oznaczenia PLANNED opisują historyczny plan. BFF pozostaje NOT RUN do F3, pełne atomic RPC do F4.

### Przygotowanie do osobnej autoryzacji

Minimalny syntetyczny kontrakt: dwa rodzaje obiektów `probe_item`, `probe_label` (id, owner UUID, sztuczna wartość), relacja m:n `probe_link` oraz oddzielny registry dla RPC. Nazwy/kolumny są **PROPOSED, wyłącznie testowe**. Relacja musi wymuszać tego samego ownera po obu stronach (np. owner-qualified klucze/FK plus RLS); zwykły FK po id nie jest autoryzacją. Nie zawiera stanowiska, statusu ani dat rekrutacji.

Proponowany przyszły zakres: `experiments/foundation/rls/`, dedykowany Drizzle config/schema/migrations, fixture A/B, HTTP integration tests. Platform przygotowuje Supabase Local i jawny DB target; Drizzle jest jedynym autorem migracji technicznego schematu, CLI nie generuje równolegle konkurencyjnej historii. SQL polityk/funkcji/grantów jest przeglądany i wersjonowany razem. PoC musi zarejestrować rzeczywiste wersje PostgreSQL, rozszerzeń i PostgREST, nie tylko wersję CLI.

Procedura walidacji migracji: (1) świeży disposable target → wszystkie migracje; (2) ponowne uruchomienie runnera → brak nowej zmiany; (3) upgrade z poprzedniego commitu z syntetycznym stanem → nowa migracja; (4) drugi niezależny świeży target → porównanie schematu/polityk/funkcji/grantów i ledgeru; (5) celowo błędna migracja w osobnym klonie → udokumentowany rollback/stop. Wynik zależy od rzeczywistych możliwości migratora — nie zakładać transakcji całej historii bez próby. Nigdy `push`/reset na niezweryfikowanym targetcie.

Domyślnie zero policy/grants = brak dostępu. Potem jawne grants tylko potrzebnych operacji do `authenticated`, RLS na wszystkich eksponowanych tabelach; `anon` nie dostaje prywatnych danych. Każda polityka sprawdza uwierzytelnionego `auth.uid()` i ownera. SELECT/DELETE używają `USING`; INSERT `WITH CHECK`; UPDATE oba warunki oraz potrzebna SELECT policy. Weryfikować owner transfer, a nie tylko zmianę wartości. Nigdy user-editable metadata jako źródło uprawnień.

### Macierz autoryzacji (każdy wiersz: PLANNED / NOT RUN)

W PR-F2 każdy przypadek wykonać bezpośrednio przez Data API z rzeczywistym JWT A/B uzyskanym przez izolowany fixture lokalnego Auth HTTP; nie wymaga to produktowego BFF. Kolumnę BFF wykonać po PR-F3/AUTH, przed PR-F6. SQL role tests są dodatkową diagnostyką, nie zamiennikiem. Tożsamość setupu admina wyłączona z fazy testowanej.

Nie każdy brak dopasowania RLS daje HTTP 403: SELECT/UPDATE/DELETE mogą zwrócić pusty rezultat. PASS wymaga braku wycieku i efektów oraz oczekiwanego rezultatu kontraktu, nie jednego uniwersalnego statusu HTTP. Constraint errors mogą ujawniać istnienie rekordów — sprawdzić zachowanie BFF i surowej Data API i ograniczyć to syntetycznymi, nieenumerowalnymi relacjami.

### Bramka DB/RLS

Zakończenie wymaga całej macierzy RLS-01–12 dla każdego rodzaju syntetycznego obiektu i relacji, powtarzalnych migracji na dwóch świeżych targetach, testu upgrade, negatywnej kontroli czułości oraz backend/security review polityk i grants. Zero dostępu B→A, zero niejawnego admin bypassu; każdy FAIL blokuje zależny user CRUD. Przejście fixture PoC nie jest certyfikacją przyszłych tabel produktu — ich macierz musi zostać ponowiona po zatwierdzeniu OPEN-002.

## 6. RPC-P0 — atomowa mutacja, idempotencja i retry

### Minimalny kontrakt proponowany do próby

Jedna funkcja `commit_probe_batch(key, payload)` dostępna przez `POST /rpc/...`, `VOLATILE`, jawnie `SECURITY INVOKER`, z pustym `search_path` i kwalifikowanymi nazwami relacji. `owner_id` pochodzi z `auth.uid()`, nie z argumentu. Wejście to kompletny zaakceptowany payload syntetyczny; parser CSV/XLSX, preview UI i pełny import pozostają poza zakresem. Uwierzytelniony user JWT i publishable key w wywołaniu; brak service-role.

Rejestr znajduje się w odrębnym `foundation_private`, poza exposed schemas Data API i poza kontraktami views/helperów. Tabele fixture i wejściowe RPC pozostają w jawnie eksponowanym schemacie PoC. INVOKER potrzebuje USAGE/DML registry dla roli wywołującej; nie twierdzimy, że właściciel nie może zmienić własnego registry przez dowolne SQL. Granicą dla zwykłego użytkownika jest brak bezpośredniego logowania SQL oraz brak publicznej arbitralnej funkcji SQL i brak ekspozycji registry. RLS registry dodatkowo izoluje A/B. Manifest obejmuje również pg_graphql (stan rozszerzenia, zakres refleksji schematów/search_path i uprawnienia), konfigurację Realtime/publications oraz wszystkie alternatywne transporty obecne w target. Nie utożsamiać braku REST exposure z brakiem GraphQL. Nieużywane transporty muszą mieć udowodniony brak dostępu (albo jawne wyłączenie w autoryzowanym PoC), nie zakładany brak funkcji. Granty registry minimalne: bez DELETE; SELECT/INSERT i tylko niezbędny zakres UPDATE, jeśli protokół zapisania wyniku go potrzebuje; brak zbędnych praw potwierdzony katalogiem i próbą SQL. Manifest grantów, exposed schemas/default privileges i wszystkich funkcji musi to wykazać; późniejsze dodanie transportu SQL/widoku/helpera uruchamia ponowne security review. Jeśli ta granica nie wystarcza, STOP wariantu i review/PO przed zmianą modelu uprawnień, bez cichego DEFINER.

Rejestr operacji: unikalność `(owner_id, idempotency_key)`; fingerprint obejmuje kanoniczny payload, jego wersję i znaczenie operacji. W jednej transakcji: zajęcie klucza → sprawdzenie istniejącego fingerprint/wyniku → walidacja i zapis wszystkich elementów/relacji → zapis wyniku. Rejestr nie zawiera trwałej kopii wierszy, pliku lub mapowania. Zakres i retencja produkcyjnego registry pozostają `OPEN-035/032`.

Konstrukcja konkurencji do testu: unikalny indeks serializuje klucz; przegrywające wywołanie odczytuje już zatwierdzony identyczny wynik albo jawny konflikt fingerprint. Nie zwraca sukcesu dla częściowego, niezatwierdzonego stanu. Nie używać ogólnego `ON CONFLICT DO NOTHING` do ukrywania konfliktów danych. Przed użyciem sprawdzić zachowanie izolacji PostgREST i blokad; zmiana na SERIALIZABLE nie zwalnia z testu retry.

Parametry 3 elementów/20 requestów to powtarzalne fixtures badawcze, nie limity produktu ani deklaracja wydajności. Dobór rzeczywistych limitów importu zależy od OPEN-007/023 i pomiarów, nie od tego fixture.

### Ograniczenia i bramka RPC

Data API nie zapewnia transakcji obejmującej N niezależnych żądań. SQL commit nie obejmuje Storage, wiadomości, jobów w innej transakcji lub komunikacji sieciowej. Przerwanie HTTP nie dowodzi rollbacku; bez registry retry jest niebezpieczny. Limit czasu i request size mogą przerwać operację, a payload musi mieścić się w pamięci oraz jednej transakcji. Nie wprowadzać trwałego stagingu, rozbijania zaakceptowanego wsadu na częściowe commity ani kolejkowania importu jako obejścia ADR-0005.

PoC zakończony po RPC-01–12 przez rzeczywisty Data API, odczycie stanu DB po awariach i niezależnym backend/security review. Dodatkowy security review jest obowiązkowy przy SECURITY DEFINER, dostępie do `auth.*`, dynamic SQL, uprzywilejowanym workerze, nowych grants, zewnętrznych efektach lub zmianie kontekstu user JWT. Potrzeba DEFINER nie jest powodem do samodzielnego podniesienia uprawnień. Niepowodzenie atomiczności/idempotencji/RLS → STOP zależnego importu; zachować dowód, przedstawić minimalną korektę w przyjętym modelu lub decyzję/ADR przed alternatywą.

## 7. Przekazanie i dowody wymagane przed biznesowym slice'em

Backend przygotowuje osobne małe PR eksperymentalne zgodnie z kolejnością w Foundation Plan; QA przed wykonaniem dopisuje pliki testów, fixture i komendy do zatwierdzonego task packet. Każdy raport podaje commit, target identity, wersje usług/SDK, manifest migracji, rzeczywiste PASS/FAIL/NOT RUN i kompletność przypadków. DoD nie obejmuje arbitralnego coverage percentage.

Wyjście PoC: sprawdzony mechanizm Auth i user context, dowód RLS A/B i transakcji, jawne luki dostawcy oraz rekomendacja do decyzji PO. Następnie trzeba zamknąć tylko zależne szczegóły OPEN i zatwierdzić rzeczywiste kontrakty danych/operacji. Publiczna rejestracja, produktowa sesja i pierwszy biznesowy slice nie wynikają automatycznie z PASS technicznego eksperymentu.
