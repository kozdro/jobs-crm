## Historyczna identyfikacja brakującego kontraktu — rozstrzygnięta DEC-061

**BLOCKED_DECISION:** integracja rzeczywistej aplikacji lub kontaktu w tym samym zatwierdzeniu co nowa sprawa. Blueprint zatwierdza cel, lecz nie ustala nowego kontraktu komendy ani nie rozszerza automatycznie DTO DEC-052. Istniejące requestId create oraz event command nie zapewniają razem jednego wyniku po utracie odpowiedzi. Dwa kolejne zapisy mogą zostawić sprawę bez faktu, choć summary pokazywało wspólny zapis.

Najmniejsze pytanie PO (przekazuje orchestrator, propozycja nie jest zatwierdzeniem):

**Czy rozszerzamy Quick Capture o jeden atomowy zapis sprawy i jawnie potwierdzonego faktu aplikowania albo kontaktu inbound/outbound, przy zachowaniu „Zapisz tylko sprawę”?**

- **A — PROPOSED, rekomendowane dla pełnej realizacji zatwierdzonych scenariuszy:** approve rozszerzenie lokalnego kontraktu DEC-052/054. Jeden request/owner-scoped intent obejmuje create+opcjonalny fakt+wynikowy status; wszystkie albo zero. Dane faktu i jawne potwierdzenie jak w 3A (opcjonalny rzeczywisty dzień/unknown, kierunek kontaktu, bez CV/uczestników/kanałów). Dup warning przed jakąkolwiek mutacją; tylko świadoma nowa sprawa, bez zapisu faktu na dopasowanej istniejącej; replay całego zamiaru bez duplikacji; zmieniony zamiar konflikt. Wymaga aktualizacji kontraktu, testów SQL/rollback/recovery i backend/security review. Techniczny projekt pozostaje do analizy po decyzji, nie do cichego wdrożenia.
- **B — zachować teraz ograniczenie wykonania, nie zmieniać Blueprintu:** wykonać niezależny hardening, rzeczywisty wybór Sytuacja i save-only z uczciwym objaśnieniem zakresu; złożony zapis Działanie pozostaje jawnie nieukończony. Rejestracja faktu jest dostępna jako odrębna świadoma czynność na istniejącej sprawie. To nie domknięcie pełnego Quick Capture, nie nowy projekt MVP i nie powód usuwania docelowych scenariuszy.

Nie proponuje się sekwencji dwóch requestów jako zamiennika atomowego sukcesu ani wyboru sytuacji jako automatycznej rejestracji działania. Potrzeba nowego kontraktu jest specyficzna dla tej integracji; nie otwiera ponownie zatwierdzonej architektury.

OPEN-002 i OPEN-024 częściowo rozstrzygnięte w DEC-052 wymagają rozszerzenia wyłącznie o zakres złożonego polecenia/duplikatów. OPEN-026/037 częściowo rozstrzygnięte dla 3A (bez kanałów, opcjonalny dzień bez godziny) nie blokują ponownie istniejących danych faktu; trzeba jawnie potwierdzić ich użycie w nowym zapisie. OPEN-004/020 są częściowo rozstrzygnięte DEC-056 i nie stanowią powodu cofania istniejących korekt. OPEN-011/025 (import/URL), OPEN-003/027 (globalne etapy) i pozostałe Calendar/Auth/privacy/public-release pozostają poza zmianą. Nie zamykać całych OPEN decyzją o jednym podzakresie.

## Minimalne zabezpieczenie procesu i handoff

Istniejący AGENTS/delivery zakazuje zmian bez decyzji, lecz sam opis ogólnej hierarchii łatwo pomylić z dowodem zgodności. Minimalny potrzebny dodatek: task packet zawiera macierz **kanoniczne źródło + wariant/status + planowane zachowanie + zgodność/wyjątek PO**; autor nie rozpoczyna zależnej implementacji przy pustej pozycji/konflikcie. Osobna sekcja review wymaga oceny tej macierzy i diffu wobec źródeł, a nie tylko testów. Wrapper powinien dołączać obowiązek odczytu macierzy/źródeł oraz raportu odstępstw; nie nadaje to narzędziu zdolności automatycznej weryfikacji semantyki ani nie zmienia uprawnień. Nie trzeba przebudowywać harnessu ani dodawać frameworka produktu.

Plan ownerów: spec-analyst dostarcza tę macierz przed kodem; frontend realizuje jedynie dopuszczony UI i unit; QA planuje/pisze E2E/regresje oraz uruchamia izolowany runtime; orchestrator posiada packet/proces/dokumentację i uzyskuje tylko rzeczywiście brakującą decyzję; niezależny frontend reviewer ocenia UX/kod/testy i zgodność Discovery/Blueprint/TD/DEC/ADR przez istniejący read-only wrapper, backend reviewer ocenia minimalną zmianę harnessu, security reviewer jeśli dotknięto uprawnień/wrażliwych granic. Złożone create+fact dopiero po decyzji PO i osobnym backend/security zakresie.

DoD planu: źródła nie są zmienione pod wykonany podzakres; rzeczywista Sytuacja i cztery kroki zachowane; save-only zawsze dostępne; pełne Działanie ma decyzję PO albo pozostaje jawnie BLOCKED_DECISION, bez udawania ukończenia; istniejące reguły/DTO/idempotencja nie są obchodzone. Raport implementacji osobno podaje exact candidate, runtime, komendy, PASS/FAIL/NOT RUN/BLOCKED i PR bez merge/deploy.

Weryfikacja tego dokumentu: PASS_STATIC odczytu podanych źródeł i kontroli planu; testy aplikacji przez tego autora NOT RUN. Brak zmiany kanonicznego DEC, ADR, FR, AC lub BR. Nie jest to niezależny code review późniejszej implementacji.
