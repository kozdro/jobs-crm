# Foundation — macierz QA i protokół dowodów

**Stan:** DRAFT / PROPOSED, 2026-10-28. **Status każdego testu aplikacji, PoC i infrastruktury w tym dokumencie: `PLANNED / NOT RUN`.** W tym zadaniu powstaje plan testów; nie aplikacja, test fixtures w bazie ani środowisko. Brak implementacji jest powodem niewykonania, a nie pozytywnym wynikiem. Lokalne ID `FQA-*` identyfikują przypadki tego planu, nie zastępują istniejących AC/TC.

Podstawa: [Foundation Plan](foundation-plan.md), [PoC Auth/RLS/RPC](foundation-pocs.md), [platforma i DR](foundation-platform.md), [OPEN i biznesowy slice](foundation-gates.md), [scaffold](foundation-frontend.md), [strategia QA](../quality/test-strategy.md), [AC](../quality/acceptance-criteria.md), [traceability](../quality/traceability.md), [ADR-0001/0003/0005/0007/0009/0010](../decisions/adr/README.md). QA przygotowuje i później implementuje integracyjne, security i E2E testy; inżynierowie piszą unit testy własnego kodu. Autor niniejszego planu QA: natywny generic subagent + kanoniczna rola qa-engineer; model/reasoning `NOT EXPOSED`. Niezależny QA review planu musi wykonać inna sesja.

## Zasady oceny i środowiska

- **L0:** świeży lokalny/CI checkout dokładnego SHA, przypięty Node/pnpm, brak `node_modules`, `.next` i lokalnych artefaktów; bez sekretów i usług. **L1:** jawnie nazwany jednorazowy Supabase Local na loopback, syntetyczne A/B/anon, manifest migracji i rzeczywiste wersje PostgreSQL/PostgREST/Auth/Storage/pgmq. **L2:** L1 + produkcyjny build BFF pod lokalnym HTTPS, dwa niezależne procesy BFF oraz oddzielne browser contexts. **G:** L2 + osobno autoryzowany testowy Google OAuth client i uprzednio przygotowane konto. **DR:** odizolowany restore target i autoryzowane testowe repozytorium kopii/niezależny ledger; bez publicznego ruchu i danych realnych.
- Setup/provisioner i migrator mogą przygotować fixture osobną rolą; faza badania RLS/RPC musi używać rzeczywistych JWT A/B/anon i user-scoped Data API. Zapytanie jako `postgres`, table owner lub BYPASSRLS nie jest dowodem izolacji. Inspekcja katalogu/grantów to uzupełnienie, nie zamiennik próby dostępu.
- Każda komórka „oczekiwanie / PASS” podaje warunek sukcesu; jego naruszenie w wykonanej próbie = **FAIL**. Nieoczekiwany wyjątek, zero wykrytych testów i pominięty warunek nie są PASS. Brak środowiska/credentials = **NOT RUN** z powodem; nieustalony zależny kontrakt = **BLOCKED**. Brak konkretnego statusu HTTP nie obala izolacji: RLS może zwrócić pusty wynik. Zawsze sprawdzić dane/metadata/efekty, nie tylko kod odpowiedzi.
- Parametry syntetyczne (3 rekordy, 20 żądań, skrócony TTL/lease) są fixtures eksperymentu, nie limitami produktu ani SLA. Wartości i warunki podać w raporcie. Przed promocją sesji wymagany zatwierdzony kontrakt OPEN-013/042/043; pomiar opóźnienia JWT sam nie ustanawia dopuszczalnego opóźnienia.
- Każdy PR-F* i późniejszy biznesowy slice mają osobną autoryzację. F1 nie wymaga DB/Auth. F2 RLS jest warunkiem integracji danych z F3. F2 uzyskuje JWT przez oddzielny fixture provisioner lokalnego Auth HTTP, bez BFF/browser auth; wiersze BFF czekają na F3 i wspólną akceptację F6. F4 można badać z fixture JWT po F2, lecz wspólny kontrakt z BFF wymaga F3. F5 jest wymagany przed użyciem workera; manual capture może wystartować po F1–F4/F6 i właściwych OPEN bez F5. DR/Storage/public signup nie blokują scaffold, ale blokują publiczny release w swoim zakresie.

## Deterministyczne awarie i kontrola czułości

QA przygotowuje testowe bariery/latch i kontrolowane proxy, wyłączone z obrazu release. Refresh race synchronizuje dwa procesy na odczycie tej samej generacji; RPC race uwalnia requesty wspólną barierą. Dla utraty odpowiedzi proxy odbiera odpowiedź upstream po commit i celowo nie dostarcza jej klientowi; observer potwierdza registry przed retry. Osobna próba zrywa połączenie przed wynikiem transakcji, po czym zawsze odczytuje registry. Kill workera następuje na markerze „read”, „effect committed” lub „before ACK”, nie po zgadywanym sleep. Test expiry/lease używa skróconej rzeczywistej konfiguracji i polling z deadline oraz obserwacji czasu usług; fake clock unit nie jest dowodem wygasania JWT/lease w realnym Auth/DB.

Lokalne kopie z celowo uszkodzoną policy/grantem, niewłaściwą rolą lub nieprawidłowym fixture służą tylko wykazaniu, że test staje się czerwony. Nie osłabiać kandydata i potem „zaliczać” próby jako security PASS. Czysty target po takim eksperymencie przygotować ponownie z tego samego manifestu. Błąd observera/setup nie może dać zero rows interpretowanego jako poprawna odmowa.

## Komendy i artefakty — istniejące vs przyszłe

W tym zadaniu dokumentacyjnym orchestrator może uruchomić istniejące kontrole: `python3 harness/scripts/sync.py --check`, `python3 harness/scripts/check.py`, `python3 -m unittest discover -s harness/scripts -p 'test_*.py' -v`, `git diff --check` oraz kontrolę względnych odnośników zmienionych dokumentów. Ich rzeczywiste wyniki raportuje oddzielnie z kandydatem; są testami harnessu/dokumentacji, nie wynikiem powyższej macierzy.

**Przyszłe skrypty do utworzenia w autoryzowanym PR, obecnie wszystkie NOT RUN:** `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, `pnpm test:unit`, `pnpm build`, `pnpm test:integration`, `pnpm test:e2e:foundation`. Kontrakt F1: typecheck = `next typegen && tsc --noEmit`; lint = `eslint . --max-warnings=0`; format sprawdza tylko zatwierdzone pliki aplikacji/config/testów bez masowego reformatowania docs/harness; unit = `vitest run`; build/start = `next build`/`next start`; E2E = `playwright test --project=foundation` na produkcyjnym starcie po build, bez reuse dev server. Dokładne pliki konfiguracyjne finalizuje scaffold; suite integracyjna dzieli się na jawne projekty RLS/Auth/RPC/queue, a DR na osobny świadomie uruchamiany protokół. F1 uruchamia jedynie dostępne unit/static/build/smoke; kolejnych suite nie zastępuje pusty test albo test z warunkowym skip. CI nie łączy NOT RUN krytycznej zależności w zbiorcze PASS. Pełny DR i real Google mają osobne credentials i oddzielne wyniki od lokalnego mock/CI.

Każdy wykonany wynik musi mieć: ID FQA oraz AUTH/RLS/RPC/AC/TC w zakresie, dokładny commit/diff i base SHA, test source/fixture hash, model/rola autora i sesji QA/reviewera, datę/czas, komendę/procedurę, exit code i liczbę faktycznie uruchomionych przypadków, target identity, wersje runtime/usług/obrazów/SDK, manifest migracji/polityk/grantów, oczekiwanie/obserwację, PASS/FAIL/NOT RUN/BLOCKED i przyczynę. Artefakty: zredagowane raporty JUnit/Playwright, liczniki/stany DB przed/po, canary scan, HTTP/header trace bez tokenów, DR timestamps/checksums. HAR/cookies/credentials/PII nie trafiają do Git ani PR. Zmiana kandydata unieważnia pokrycie dotkniętych kontraktów i wymaga ponowienia.
